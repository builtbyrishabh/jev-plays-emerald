Jev Plays Emerald · System Explainer

How a model that can't
see pixels plays Pokémon.

Built from first principles: start with what the model cannot do, and derive every piece of the system as the minimum needed to close that gap.

01 — THE PROBLEM

Three things that don't fit together

Before any code, state the mismatch precisely. Everything else is a consequence.

Pokémon Emerald is a Game Boy Advance ROM. It runs at 60 frames per second, its entire world lives in a few hundred kilobytes of binary RAM, and it accepts exactly ten inputs: the D-pad, A, B, Start, Select, L, R.

Jev is a hosted model behind an HTTP endpoint. It takes roughly half a second to a second to answer, it has no memory between calls, and it reads JSON.

Put them side by side and three specific impedance mismatches fall out:

Mismatch 1 — Representation. The game's state is raw memory addresses. The model needs facts. Nothing in 0x02024A54 means "Torchic has 20 HP" without a decoder.

Mismatch 2 — Granularity. The game consumes button presses. A useful decision is "walk to Oldale Town." Between those two sits a pathfinder, not a model. Asking a model to emit 400 D-pad presses is both wasteful and hopeless.

Mismatch 3 — Time. The game will not wait. During one ~600 ms model call, 36 frames go by. Whatever the model was looking at may no longer be true when its answer lands.

So the system is not "an AI playing Pokémon." It is three bridges, each one solving exactly one mismatch — and a model sitting in the middle doing a smaller job than you'd expect.

Observation

→
Jev
Picks one option from a menu. Returns a probability distribution.
→

The loop that wraps all three solves time — and it turns out to be the hardest part.

02 — BRIDGE ONE

What Jev receives

Not pixels. Not a screenshot. A decoded snapshot of the world as structured facts.

Every single frame, ObservationReader.read() reaches into PokéBot's memory decoders and builds one immutable Observation. This is the model's entire window onto the world:

FieldWhat it carries
game_stateOVERWORLD, BATTLE, CHOOSE_STARTER, NAMING_SCREEN, TITLE_SCREEN…
positionMap group/number, local (x, y), facing direction
menu_phase
battle_phase		Which menu is open; whose turn it is inside a battle
partyEvery Pokémon: species, level, HP/max, status, and each move with PP, type, power, accuracy, description
opponentSpecies, level, HP/max, status — when in battle
active_battlerWhich party slot is out, and which of its moves are legally usable this turn
inventoryEvery bag pocket flattened to name + quantity
opening_flags5 story booleans: rescued_birch, received_pokedex, defeated_rival_route103, set_wall_clock, rival_left_for_route103
recent_outcomesThe last 12 actions and how each ended — the model's only memory
tasks / scriptsWhich engine routines are currently running (how we detect cutscenes)
can_runWhether escape is actually possible, computed from the real escape-chance formula

The one non-obvious field: context_id

A 16-character SHA-256 hash of a deliberately chosen subset of the state — game state, map, menu phase, battle phase, party, inventory, flags, battlers. Coordinates are excluded on purpose.

Why exclude position? Because walking changes (x, y) sixty times a second. If the id churned every frame, every model answer would arrive already expired. The context_id answers a sharper question — "is this still the same decision situation?" — not "is this the same frame?" It becomes the system's entire correctness mechanism in §6.

One honest caveat is shipped inside the payload as observation_note, so the model never over-trusts its window:

"HP values are exact observations read from game memory.
 Opponent moves and future random outcomes are not provided."
03 — BRIDGE TWO

What Jev is allowed to say back

Here's the design decision that makes the whole thing tractable.

The model never emits a button. It never emits free text. It never emits a plan. It picks one ID from a list we hand it — and that list contains only actions that are legal right now, in this exact state.

Each action ID maps to an ExecutionPlan: a Python generator that yields once per emulator frame, plus a declaration of which game states it's allowed to run in.

ActionBecomes
starter:treeckoNudge the cursor left, press A until a party member exists, then verify the acquired species actually matches — or raise
battle-move:0Drive the battle menu to move slot 0 and confirm
goal:oldaleFull pathfind to Oldale Town — hundreds of frames of walking, with stall detection
heal:oldaleEnter the Pokémon Center, heal, then assert HP, status and PP are all actually restored
dialogue:advanceHold the right button through a cutscene until the script stack empties
battle-runScroll to RUN and confirm — refuses outright if escape chance is zero
setup:nameA fixed 16-button keyboard sequence to type "JEV". Configuration, never a model choice.

The labels are not terse IDs — they're written to be self-explanatory, because they're the only description of the options the model gets. Real text sent during a battle:

{
  "battle-move:0": "Use Pound (Normal, 35/35 PP, 100% accuracy, 40 power).
                     Pounds the foe with forelegs or tail.",
  "battle-move:1": "Use Leer (Normal, 30/30 PP, 100% accuracy).
                     Frightens the foe with a leer to lower DEFENSE."
}

Illegal moves are filtered out before the model ever sees them — zero PP, disabled, or blocked by the engine. The model cannot choose a bad action because a bad action is never on the menu. This is the difference between validating output and constraining it.

04 — THE MODEL

Jev isn't a chatbot

This is the part most people get wrong about the project.

Jev is reached at typesafe-ai/jev through Vercel AI Gateway's evaluation-model endpoint. It is not a text generator with a JSON mode bolted on. Its native output is a probability distribution over labelled options.

We send

state + one question

  • The full Observation as JSON
  • A choice question
  • criteria: the legal ID → label map
  • A static instruction string
We get back

a distribution

  • The chosen ID
  • A probability for every option
  • A confidence score
  • Token usage
// POST https://ai-gateway.vercel.sh/v4/ai/evaluation-model
{
  "state": { /* the whole Observation from §2 */ },
  "questions": {
    "action": {
      "type": "choice",
      "instructions": "...the mission, see §5...",
      "criteria": {
        "starter:treecko": "Choose Treecko",
        "starter:torchic": "Choose Torchic",
        "starter:mudkip":  "Choose Mudkip"
      }
    }
  }
}

A real answer, from your own run log

Pulled verbatim from .cache/task3-live-decisions.jsonl — the moment Jev picked a starter:

Distribution returned
starter:treecko0.51
starter:torchic0.29
starter:mudkip0.20

Notice the confidence is 0.27 while the top probability is 0.51. The model is telling you it genuinely isn't sure — all three starters are viable, and it knows it. That signal is preserved rather than flattened away.

Every answer is checked before it can move a single pixel

validate_choice() rejects the response outright unless all of this holds:

  • the answer type is exactly "choice"
  • the chosen ID is one we actually offered
  • the probability keys are exactly our legal ID set — no extras, none missing
  • every probability is finite and non-negative
  • they sum to 1.0 within 0.01
  • confidence, if present, sits in [0, 1]

Anything else raises, and the run pauses for a human. The model is trusted to have taste, never trusted to be well-formed.

05 — THE INSTRUCTIONS

Is it guided step-by-step?

The honest answer is: half. And the half matters.

First, here is the complete, verbatim instruction passed to Jev. Not an excerpt — this is all of it, it is a constant in the source, and it is byte-identical on every call from the title screen to the final rival battle:

"Your mission is to acquire a starter, rescue Birch, and win the
 first rival battle on Route 103. Choose exactly one legal action
 for the current Pokemon Emerald state. Treat the probabilities as
 your preferences over the offered actions."

Three sentences. A goal, a format rule, and a semantics note. That's the entire prompt.

So no — there is no step-by-step script in the prompt. The model is never told "now go upstairs," never given a hint about the next step, never shown a plan, never told what it did last turn beyond the raw outcome list. It gets a mission and a menu.

But the route is absolutely guided — in the code

The step-by-step-ness is real. It just lives in opening.py, not in the prompt. _opening_actions() is a hand-written state machine keyed on map ID and story flags, and for most of the opening it returns exactly one legal action:

if here == INSIDE_OF_TRUCK:      → "Step out of the moving truck"
if here == own_house_1F:        → "Set the bedroom clock" / or leave home
if here == own_house_2F:        → "Interact with the bedroom clock"
if here == rival_house_1F:      → "Meet the new neighbor upstairs"
if not observation.party:       → "Investigate Birch's call for help"
if here in {LITTLEROOT, RT101}:  → "Travel to Oldale Town"

And here is the consequence that ties it together:

When only one action is legal, Jev is not called at all. The loop takes the single option directly and records the decision as source: "deterministic" — no HTTP request, no tokens, no latency. Walking through Littleroot costs nothing because there was never a decision to make.

Which means Jev is consulted at exactly four kinds of fork in this scope:

3
Which starter — Treecko, Torchic, Mudkip
2–4
Which move, every battle turn
2
Heal at the Center first, or go fight
+1
Flee, when escape is actually possible

The split, stated plainly: navigation is authored, tactics are free. The code decides where you are allowed to stand; Jev decides what you do when standing there matters.

06 — BRIDGE THREE

Solving time: one decision, frame by frame

The model takes ~600 ms. The game runs at 16.7 ms per frame. Here's how that gap is survived.

frame 0
Read RAM → build Observation. Compute context_id. Compute legal actions: 2 moves available.
frame 0
More than one option → fire the HTTP request on a single-slot worker thread. A second concurrent request is structurally impossible; the worker raises if one is already in flight.
frames 1–35
The emulator keeps running. Every frame, held buttons are explicitly released so a stale input can't leak through while we're thinking. The loop keeps observing.
frame 36
Answer arrives. Now the critical test — is it still valid?
frame 36
Four staleness checks: are we paused? did the generation counter move? does the context_id still match? is the legal action set unchanged? Any one fails → the answer is discarded, logged, and re-asked against fresh state.
frame 37+
Valid → the action's generator starts, advancing one step per frame, re-checking its guards every single frame.

That discard path is not theoretical. Your own runs/decisions.jsonl logged 15 discarded answers — 15 times the world moved while Jev was thinking, and the system correctly threw the answer away instead of acting on a stale belief.

Rails that hold while an action runs

GuardBehaviour
context changedChecked before execution starts — action fails rather than acting on a stale premise
state escapeGame state leaves the plan's allowed set (a wild battle interrupts a walk) → INTERRUPTED, buttons released
unexpected menuA menu opens that this plan didn't expect → INTERRUPTED
frame_limit 360060 seconds of wall clock. Nothing can hang the run forever.
stall detection45 overworld frames with no movement → replan the path (max 2 replans, then fail)
pauseHonoured on the next frame boundary, mid-action, with inputs released
retry policyOnly timeouts, 429 and 5xx retry, and at most twice. A wrong answer is never retried into existence.
any FAILEDThe run pauses itself and waits for a human. It does not guess.

Interruptions aren't just abandoned, either. The interrupted action is remembered, and once the world settles it is re-validated against the new legal set — resumed only if it's still a legal thing to want.

07 — THE SCORECARD

Who actually does the work

Worth being blunt about, because it's the most interesting thing in the design.

The harness decides

  • Where to walk, and the whole route through the opening
  • Which actions are legal at all
  • How every intent becomes button presses
  • When to ask, and when not to bother
  • Whether an answer is still valid on arrival
  • When to stop and call a human
  • Typing the name, setting the clock, advancing cutscenes

Jev decides

  • Which starter to take
  • Which move to use, every battle turn
  • Whether to heal before the rival fight
  • Whether to flee a wild encounter

Small surface. But it's the surface where judgement actually matters — and the one place a scripted bot would need a hand-tuned heuristic instead.

This is the real architectural claim of the project: the model is a policy, not a driver. It's consulted at forks and constrained everywhere else. That's what makes the run reproducible, auditable, cheap, and safe to leave running.

08 — IN ONE BREATH

The whole system

Every frame, decode RAM into typed facts and hash them into a context_id. Compute which actions are legal right now. If exactly one is legal, just do it — no model involved. If several are, send the facts plus that menu to Jev with a fixed three-sentence mission, on a single-slot worker so the emulator never blocks. When the distribution comes back, validate its shape, then check the world hasn't moved underneath it — discard it if it has. Otherwise turn the chosen ID into a generator that advances one frame at a time, re-checking its guards continuously, and pause for a human the moment anything fails.
